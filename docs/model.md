# Модель расчёта

Источник синтетических данных: предоставленный датасет районов. Все значения хранятся в `backend/data/simulation.json`; числовые правила не дублируются в браузере.

## Показатели и веса

Все показатели направлены одинаково: **100 — лучше**, **0 — хуже**. Веса:

| Направление | Показатели | Вес направления |
|---|---|---:|
| Транспорт | T1, T2 | 0,20 |
| Экология и озеленение | E1, E2 | 0,20 |
| Социальная сфера | S1, S2 | 0,22 |
| Безопасность | B1, B2 | 0,18 |
| Городские сервисы | C1, C2 | 0,20 |

Районный балл: `D_d = Σ(w_k × I'_dk)`. Городской средний: `D_avg = Σ(pop_d × D_d)`. Финальный балл: `Score = 0.7 × D_avg + 0.3 × min(D_d) − N_crit`.

`N_crit` — количество пар «район × показатель» со значением строго меньше 40 после мероприятий. Значение ровно 40 штрафа не даёт. Округляется только отображение результата; промежуточные вычисления используют полную точность.

## Эффекты инициатив

Полный эффект меры масштабируется по лагу: `(8 − L) / 8`. Например, при лаге в 3 квартала реализуется `5/8` эффекта. Районная мера влияет только на выбранный район, городская — на все районы.

Каталог интерфейса показывает уже **реализованную долю** эффекта (например, M7: S1 +10 вместо полного +16). Значения для каталога рассчитывает сервер; итог дополнительно учитывает синергии и ограничение 0–100.

Синергии фиксированы и не масштабируются по лагу:

- M1 + M2: T1 +2 в районе M1;
- M10 + M12: B1 +2 в районе M10;
- M5 + M6: E2 +2 в районе M5.

Значения показателей ограничиваются диапазоном 0–100 после суммирования эффектов и синергий. Отрицательные эффекты, например T1 −2 от M11, сохраняются до этого ограничения.

## Ограничения сценария

- бюджет: 100 условных единиц;
- ровно 5 разных мероприятий, каждое можно выбрать один раз;
- не более 2 мероприятий из одного направления;
- районные меры требуют район, городские меры не принимают район;
- M1 и M3 несовместимы в любом районе;
- M4 и M7 нельзя выбрать для одного района;
- M5 и M13 нельзя выбрать для одного района;
- недопустимый сценарий не получает Score.

Пустой план используется только для базового результата; пользователю нельзя запустить его как итоговый сценарий.

## Подбор альтернатив

После расчёта система перебирает варианты с **одной заменой**: заменить инициативу либо перенести районную меру в другой район. Каждый кандидат проходит тот же валидатор и рассчитывается тем же scoring engine. Показываются до трёх допустимых вариантов с более высоким отображаемым (округлённым до сотых) Score, отсортированных по Score и затем стоимости.

Это локальный поиск по одной замене, а не доказательство глобально оптимального бюджета. Если улучшение не найдено, приложение сообщает только, что нет лучшего варианта среди одиночных замен.

## Контрольные значения

| Проверка | Результат |
|---|---:|
| Базовый городской средний `D_avg` | 56,8624 |
| Базовый слабейший район | Нура: 49,18 |
| Базовые критические пары | 2 |
| Базовый Score | 52,55768 → 52,56 |
| M7 Нура + M8 Нура + M10 Нура + M12 город + M5 Сарыарка | 95 единиц |
| Score контрольного сценария | 56,54307 → 56,54 |
| Точное изменение относительно базы | +3,98539 |
| Разница отображаемых Score (`56,54 − 52,56`) | +3,98 |
| Критические пары контрольного сценария | 0 |

Контрольный пример запускается тестами в `backend/tests/test_engine.py` и `backend/tests/test_api.py`.

Точные Score и дельты сохраняются без округления. В интерфейсе Score показывается до сотых, а визуальная дельта рассчитывается как разность показанных Score, чтобы совпадать с числами на экране; исходная дельта остаётся в API.
